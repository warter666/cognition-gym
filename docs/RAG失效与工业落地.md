# RAG 失效模式与工业落地手册

> 回答两个问题：①"库太小没暴露召回/幻觉问题"该怎么答；②RAG 从 demo 到工业要补什么。
> 配套实现：`evals.py::eval_retrieval`（recall@k/MRR）、`session.py` 无召回显式降级。

---

## 一、核心应答原则（背下来）

**错误姿态**：辩解"我的库小、场景简单，所以没这些问题"。
——评审听到的翻译是：问题存在，但我没测过，赌它不出现。

**正确姿态**：失效模式的出现是**频率问题，不是种类问题**。库大 100 倍不会产生新的失效类型，只会让低频类型高频化。所以正确的工程顺序是：**先把失效模式分类学、检测信号、测量手段建好，再让规模来涨**——我库小，但我的检测先于规模存在。

一句话版本：
> "我没遇到，不是因为没有，而是因为小库让问题没有经济动力出现。我展示了三类失效模式的检测信号和测量工具，它们已经在仓库里跑，规模上去时告警先于事故。"

## 二、本项目 RAG 失效模式分类学（检测 → 缓解 → 测量）

### A. 召回失败（该检到的没检到）
- **在本项目里的两个后果**：
  1. **路由错**：热度路由检索无命中 → 误判非热门 → 模式选错；
  2. **锚定失效（更严重）**：M1 生成需要"主流共识靶子"做事实校验基准，检索为空时模型用自带知识充当共识 → 事实错误风险无界。
- **检测信号**：命中数=0 / 相似度低于阈值 / 路由落 gray 带。
- **已有缓解**：冷启动退化为领域频率兜底；gray 带走 LLM 兜底并回写；M2 用用户粘贴源绕开检索依赖。
- **本次新增**：无命中时**显式降级**——生成的上下文注入"未锚定"声明，答案卡存库时带 `anchored: false` 标记，该轮自动进入人工复核名单。**绝不静默 fallback**，这是与玩具实现的最大区别。
- **测量**：`evals/retrieval_golden.json` 黄金集 + recall@k / MRR，换 embedding 模型或改检索逻辑必须回归。

### B. 召回噪声（检到不相关的）
- **后果**：污染生成上下文，诱导"看起来有依据"的幻觉（比没检索更危险）。
- **检测**：注入 token 占比监控；人工抽检上下文相关性。
- **缓解**：top-k 限制；"热度卡"预先把长文压成结构化短块（比通用 chunking 噪声低）；R2 加 cross-encoder 重排。

### C. 生成层幻觉
- **三层已建**：检索锚定（事实必须与检索一致）→ 分类表硬约束（只能歪论证不能歪事实）→ 代码断言（quote 必须逐字在正文）。
- **残余风险与答案**：断言保证"可批改性"，不保证"事实真实性"——真实性靠 LLM judge 抽检（`gym eval --live` 的边界检查可扩展 anchor 核对），以及 anchored=false 轮次的人工复核队列。

### D. 知识过时
- 时间衰减排序（30 天半衰期）+ 每周策展增量入库 + 卡片必带 date 字段。检索结果陈旧是**可观测**的（按日期分布出告警），不是可议论的。

### E. 答案卡幻觉（本项目特有）
- quote 不在正文 / 谬误超表 → 作废重试，两次失败丢弃。已硬门，单测覆盖。

## 三、被追问时的三段式话术

1. **承认**："召回失败和检索噪声在真实规模下必然出现，我按失效模式分类管理，不按祈祷管理。"
2. **展示闭环**：每一类失效都对应"检测信号 → 已实现的缓解 → 测量工具"三者，并举 A 类为例走一遍。
3. **给出触发条件**："recall@k 黄金集回归进评测门禁；线上命中数和得分分布进日志；无召回轮次自动标记人工复核。问题从'没遇到'变成'遇到时当轮就亮红灯'。"

## 五、检索评测的用法（本次已实现）

```bash
python apps/cli.py eval --retrieval   # 对黄金集算 recall@5 与 MRR
```

黄金集格式（`evals/retrieval_golden.json`）：每例 = 检索关键词 + 应命中的 dedup_key 列表。
指标：recall@k（前 k 条里捞到几成该捞的）、MRR（该捞的排得多靠前）。
**门禁建议**：recall@5 < 0.8 时禁止替换检索组件上线——和 kappa ≥0.7 同级的硬门。
